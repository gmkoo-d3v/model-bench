# 桜の庭 — Voxel Pagoda Garden 벤치마크

요즘 LLM 벤치마크로 유행하는 "단일 HTML 복셀 정원" 과제를 여러 모델에 똑같이 시키고, 결과물을 브라우저에서 직접 띄워 검증한 기록입니다.

과제의 원형은 하늘에 떠 있는 복셀 섬 위에 5층 목탑·토리이·벚나무·잉어 연못을 올리고, 꽃잎이 흩날리며 낮/밤이 순환하는 Three.js 데모입니다. 원본 영상에서 프레임을 뽑아 요구사항을 [`SPEC.md`](SPEC.md)로 정리했고, 모든 모델에 [`prompt.txt`](prompt.txt)와 함께 그대로 전달했습니다.

> [!WARNING]
> **codex CLI로 돌린 GPT 모델 넷은 브라우저로 자기 결과물을 확인할 수 없었습니다.**
> 감독자가 `approval_policy="never"`와 `workspace-write` 샌드박스로 실행했기 때문입니다. 브라우저 자동 제어는 승인 단계에서 자동으로 거절됐고, 샌드박스 안에서는 three.js를 받아올 CDN 네트워크도 막혔습니다.
> 반면 Claude 서브에이전트는 처음부터 브라우저 패널을 쓸 수 있었습니다.
> 코드 결함은 모델 책임이지만, **그 결함을 스스로 발견할 기회는 공평하게 주어지지 않았습니다.** 자세한 내용은 [브라우저로 자기 결과물을 봤는가](#2-브라우저로-자기-결과물을-봤는가) 절에 있습니다.
>
> 같은 넷을 브라우저를 쓸 수 있는 **Codex 앱**에서 다시 돌렸더니 **검은 화면은 한 번도 나오지 않았습니다.** 다만 모델당 한 번씩만 돌린 결과라, 그 차이가 전부 브라우저 덕인지는 단정할 수 없습니다. [codex CLI와 Codex 앱 비교](#codex-cli와-codex-앱-비교)를 보세요.

## 등급 기준

- **A** — 사양 전 항목 동작, 눈에 띄는 결함 없음
- **B** — 전 항목 동작, 사소한 결함 1–2개 (프레이밍·규모)
- **C** — 동작하지만 사용자가 바로 마주치는 결함 있음
- **F** — 첫 화면부터 결과물이 보이지 않음

등급은 **모델이 내놓은 그대로**를 기준으로 매겼습니다. 사용자가 받는 건 그 파일이기 때문입니다.

## 검은 화면을 고쳐주면 순위가 바뀌는가

Astra와 Luna는 `vertexColors` 한 단어만 바꾸면 정상으로 돌아옵니다. 그 패치본까지 같은 줄에 세우면 상위권은 이렇게 갈립니다.

| 기준 | 앞서는 쪽 |
|---|---|
| UI 패널 완성도 | **Astra(패치)** ≥ Sol > Sonnet ≈ Opus |
| 장면 풍성함 | **Sonnet** > Sol ≈ Astra(패치) > Opus |
| 탑 조형 | Astra(패치) ≈ Sol ≈ DeepSeek |
| 연못 | **Sol** > Sonnet > Astra(패치) ≈ Opus |
| 카메라 프리셋 | **Sol ≈ Opus** > Sonnet(빽빽함) > Astra(패치, 5번 처마에 걸림) |
| 엔지니어링 견고성 | **Opus ≈ Sonnet** (브라우저로 직접 보고 고침) > 나머지 |
| 비용 | Terra·Luna(≈ 8–9분) … Sonnet(74분, 42만 토큰) |

패치 기준으로 보면 **Astra는 1위 후보 셋(Astra·Sol·Sonnet) 중 하나**입니다. UI를 가장 중시하면 Astra, 결함 없는 균형이면 Sol, 장면의 풍성함이면 Sonnet입니다. 어느 하나가 모든 축에서 앞서지는 않습니다.

다만 패치본의 점수는 모델 혼자 낸 점수가 아닙니다. 결함을 찾고 고친 건 검증자였고, 모델은 검은 화면을 "완료"로 보고했습니다.

## codex CLI와 Codex 앱 비교

같은 GPT 넷을 같은 `SPEC.md`, 같은 `max` 추론으로 **실행 경로만 바꿔** 두 번 돌렸습니다. 가장 큰 차이는 앱에서는 Playwright로 브라우저를 쓸 수 있었다는 점입니다.

| 모델 | CLI — 브라우저 막힘 | Codex 앱 — 브라우저 사용 가능 |
|---|---|---|
| gpt-6-astra | **F** · 검은 화면 · 2,036줄 | B · 1,080줄 · 3번 프리셋 가림 |
| gpt-6-luna | **F** · 검은 화면 · 1,796줄 | B · 336줄 (압축된 코드) · 3번 프리셋 가림 |
| gpt-6.1-sol | **A** · 2,100줄 | B · 932줄 · 3번 가림, 5번 처마에 걸림 |
| gpt-6.1-terra | B · 1,544줄 · 첫 화면 잘림 | **A** · 776줄 |

읽을 수 있는 것:

- **검은 화면은 앱에서 한 번도 나오지 않았습니다.** CLI에서 F였던 Astra·Luna가 앱에서는 둘 다 색이 정상이고, `vertexColors`를 아예 쓰지 않았습니다.
- **Terra는 보고 고친 직접 증거가 남아 있습니다.** 앱 작업 폴더의 Playwright 콘솔 로그에 Terra 파일명과 줄 번호가 찍힌 `TypeError`가 있고, 파일은 그 3분 뒤에 다시 저장됐습니다. 나머지 셋도 페이지 스냅샷 시각이 각 파일 저장 시각과 겹쳐 브라우저를 쓴 것으로 보이지만, 로그에 파일명이 없어 추정입니다.
- **앱 결과물이 전부 짧습니다.** CLI 1,544–2,100줄, 앱 336–1,080줄입니다.
- **브라우저가 있다고 항상 나아지지는 않았습니다.** Sol은 CLI 쪽이 더 좋았습니다. 앱 버전은 프리셋 두 개가 대상을 제대로 못 잡습니다.

주의할 점:

- **모델당 한 번씩만 돌렸습니다.** 모델 출력은 실행마다 달라지므로, 위 차이를 전부 브라우저 덕으로 돌릴 수는 없습니다. 같은 조건을 여러 번 돌려야 분리됩니다.
- 앱 실행은 사용자가 했고 실행 로그가 없어 소요 시간·토큰은 모릅니다. 앱 작업 폴더에 남은 `SPEC.md` 사본이 이 폴더의 `SPEC.md`와 바이트 단위로 같은 것은 확인했습니다.

**같은 사양서, 같은 프롬프트, 같은 검증 기준**을 썼습니다. 하네스가 갈리므로 결함의 책임은 경로별로 다르게 읽어야 합니다.

- **codex CLI (GPT 넷) — 코드 결함은 모델 책임입니다.** OpenAI의 자체 하네스이고, 넷 다 같은 버전·같은 추론 강도·같은 샌드박스·같은 프롬프트였습니다. 그 안에서 Sol·Terra는 맞는 코드를, Astra·Luna는 검은 화면이 나오는 코드를 썼습니다. 하네스가 원인이라면 넷이 같이 틀렸어야 합니다.
- **OpenCode (qwen) — 결함을 모델에만 돌리기 어렵습니다.** 서드파티 에이전트 루프와 서빙 환경이 함께 작용합니다.
- **자기 확인 기회는 경로마다 달랐습니다.** codex CLI는 감독자 설정 때문에 브라우저가 막혔고, Codex 앱과 Claude 서브에이전트는 브라우저를 쓸 수 있었습니다. 아래 [2번 절](#2-브라우저로-자기-결과물을-봤는가)을 보세요.



## 검증 방법

모델이 스스로 보고한 VERIFICATION은 참고만 하고, 아래를 전부 직접 다시 했습니다.

1. `SPEC.md`의 `node -e` 검증 커맨드 재실행
2. 로컬 HTTP 서버로 띄워서 콘솔 에러 확인 (`file://`로는 ES 모듈이 안 돌아갑니다)
3. 첫 화면 스크린샷, 상태줄의 복셀 수·fps 확인
4. 카메라 프리셋 1–5를 키보드로 눌러 각각 스크린샷
5. Time 슬라이더를 21:30으로 밀어 밤 장면·반딧불이 확인
6. Regenerate seed, Wireframe 토글

## 모델별 분석

### gpt-6.1-sol · max · CLI — A

사양 범위 안에서 가장 균형이 좋습니다. 축 하나에서 1등은 아닐 수 있어도 약점이 없습니다.

- **첫 화면 프레이밍이 처음부터 맞습니다.** Luna·Terra·qwen이 섬을 잘라먹었고 정답지도 처음엔 그랬는데, Sol은 첫 로드부터 섬 전체가 여유 있게 들어옵니다.
- 연못이 제대로 된 규모입니다. 물빛에 깊이 그라데이션이 있고 나무다리가 가로지릅니다.
- 탑 상륜부를 금색 링 여러 단으로 쌓아 가장 정교합니다.
- UI 카피("LIVING GARDEN", "FIND A LITTLE PERSPECTIVE"), 시드 표시, `Shift + drag to pan` 안내까지 넣었습니다.
- 브라우저 확인을 두 번 시도했지만 **접근 거부와 CDN DNS 실패로 막혔습니다**(감독자의 승인·샌드박스 설정 때문). 로그에 `[blocked]`로 정직하게 남겼습니다. 눈으로 못 보고도 올바른 코드를 쓴 경우입니다.
- 약점: 카메라 이징이 프레임 누적 방식이라 창이 백그라운드로 가면 프리셋 이동이 길게 늘어집니다.

### claude-opus-5.5 · max — A

가장 짧은 코드로 가장 견고한 결과를 냈습니다.

- **1,198줄로 정답지 다음으로 짧은데** 사양 전 항목이 동작합니다.
- **카메라 이징을 `performance.now()` 기준으로 짰습니다.** `dt` 누적으로 짠 CLI Sol·CLI Terra·DeepSeek·qwen은 저프레임 환경에서 카메라가 제때 도착하지 않습니다. 정답지도 처음엔 `dt` 누적으로 짰다가 검증 중에 고쳤습니다.
- `vertexColors: true`를 반딧불이 Points에만, 그것도 color 속성을 직접 만든 뒤에 썼습니다. InstancedMesh에는 쓰지 않았습니다. Astra·Luna가 넘어진 자리를 정확히 비켜갔습니다.
- **스스로 브라우저로 확인하고 고쳤습니다.** 처음엔 연못·토리이·벚꽃 프리셋이 구조물 안에 박혀서 다시 잡았고, 다리 난간도 얇게 바꿨다고 보고했습니다. 정답지를 만들 때 밟은 것과 같은 두 가지입니다.
- 약점: 연못이 작고 벚나무가 성겨서 섬이 다소 휑합니다.
- 부분 확인: 에이전트가 144fps를 봤다고 보고했습니다. Opus 파일에서는 쓰로틀 때문에 29–76fps로만 찍혀 직접 확인하지 못했지만, 같은 검증 환경에서 쓰로틀이 풀린 순간 Sonnet 파일이 144fps를 찍었으므로 화면 주사율 상한으로서 그럴 만한 숫자입니다.

### gpt-6.1-terra · max · CLI — B

codex CLI로 돌린 GPT 네 개 중 가장 빨리 끝났고(≈ 9분, 토큰 76,728로 최소), 결함 없이 동작합니다.

- `vertexColors` 함정을 피했습니다. 소스 전체에 0건입니다.
- 프리셋 3·5 모두 구조물 밖에서 대상을 제대로 잡습니다.
- 브라우저 확인이 **승인 거부로 막히자**(감독자 설정 때문) Node에서 WebGL 렌더러를 모의로 띄워 대체 검증을 했습니다. 그러고도 로그에 "실제 렌더링과 60fps는 `[uncertain]`"이라고 적었습니다. 확인 못 한 것을 확인했다고 하지 않았습니다.

## 이 과제가 걸러내는 것

### 1. `vertexColors` 함정 — 정적 검증으로는 절대 안 잡힌다

열세 개 중 두 개, **codex CLI로 돌린 Astra와 Luna**가 걸렸습니다. 둘 다 사양서 검증 커맨드를 통과했고, 콘솔 에러도 없고, 60fps로 돌고, 복셀 수도 정상입니다. **화면을 눈으로 봐야만 보이는 결함**입니다. 같은 두 모델을 Codex 앱에서 돌린 결과물에서는 나오지 않았습니다.

반대쪽 끝에는 Gemini가 있습니다. 같은 프롬프트만 받고도 InstancedMesh 머티리얼 바로 위에 "여기에 `vertexColors: true`를 켜지 말 것"이라는 주석을 달았습니다. 이 함정을 알고 있었다는 증거입니다.

```js
// ❌ InstancedMesh + setColorAt()에 이걸 켜면 전부 검게 나온다
new THREE.MeshLambertMaterial({ vertexColors: true })

// ✅ instanceColor는 플래그 없이 자동 적용된다
new THREE.MeshLambertMaterial()

// ✅ vertexColors는 지오메트리에 color 속성이 있을 때만
geometry.setAttribute('color', new THREE.BufferAttribute(colors, 3));
new THREE.PointsMaterial({ vertexColors: true })
```

### 2. 브라우저로 자기 결과물을 봤는가

결과가 가장 크게 갈린 지점이고, **조건이 공평하지 않았던 지점**이기도 합니다. 시도 횟수와 막힌 이유는 각 모델의 실행 로그에서 확인했습니다.

| 모델 | 확인 시도 | 막힌 이유 | 결과 |
|---|---|---|---|
| claude-opus-5.5 | ✅ 브라우저 패널 사용 | — (보고 고침) | A |
| claude-sonnet-5.5 | ✅ 브라우저 패널 사용 | — (보고 고침) | A |
| GPT 넷 · Codex 앱 | ✅ Playwright 사용 (Terra는 로그로 확인, 나머지 셋은 시각으로 추정) | — | Terra A, 나머지 B · **검은 화면 0건** |
| gpt-6.1-sol · CLI | 2회 시도 | ❌ 브라우저 접근 거부 + **CDN DNS 실패** | A (보지 않고도 맞음) |
| gpt-6.1-terra · CLI | 2회 시도 | ❌ 컴퓨터 사용 승인 거부 → Node에서 WebGL 모의 테스트로 대체 | B (보지 않고도 맞음) |
| gpt-6-astra · CLI | 2회 시도 | ❌ 브라우저 도구 승인 거부 → 다른 경로로 재시도 중 **할당량 초과** | **F — 검은 화면 그대로** |
| gpt-6-luna · CLI | **0회** | — 시도하지 않음 | **F — 검은 화면 그대로** |

**codex 쪽 차단은 감독자가 만든 환경 탓입니다.** 막힌 경로가 두 겹이었습니다.

1. **승인 단계** — `approval_policy="never"`로 실행해서, 승인이 필요한 브라우저 자동 제어는 사람에게 묻지 않고 전부 자동 거절됐습니다.
2. **네트워크** — `workspace-write` 샌드박스는 기본적으로 네트워크가 꺼져 있습니다. 브라우저가 떴더라도 페이지가 three.js를 CDN에서 받아오지 못해 빈 화면이었을 겁니다. Sol 로그의 "CDN DNS 조회도 실패"가 이것입니다.

Claude 서브에이전트에게는 처음부터 브라우저 패널과 네트워크가 열려 있었습니다. 그래서 이 표는 "누가 더 꼼꼼했나"보다 **"볼 수 있었던 쪽과 없었던 쪽"**의 비교에 가깝습니다.

그 조건을 감안해도 읽을 수 있는 건 있습니다.

- **Sol·Terra는 보지 못하고도 맞는 코드를 썼습니다.** Terra는 브라우저가 막히자 Node에서 WebGL 렌더러를 모의로 띄워 대체 검증까지 했고, 그것이 실제 GPU 테스트가 아니라는 점도 로그에 명시했습니다.
- **Astra는 막힌 뒤에도 다른 경로로 다시 확인하려 했습니다.** 그러다 할당량에 걸렸습니다. 승인만 열려 있었다면 검은 화면을 보고 고쳤을 가능성이 높습니다.
- **Luna는 시도 자체를 하지 않았습니다.** codex 넷 중 유일하게 환경 탓으로 돌릴 수 없는 경우입니다.

### 3. 카메라가 구조물 안에 박힌다

프리셋 좌표를 대상 근처로 잡으면 나무 캐노피·토리이·탑 처마 안으로 카메라가 들어갑니다. qwen은 3개, Astra(패치)와 Gemini는 1개씩 걸렸습니다. Opus와 정답지는 처음에 똑같이 걸렸다가 눈으로 보고 고쳤습니다.

카메라는 밖에 있어도 대상이 가려지는 경우도 있습니다. Codex 앱 결과물은 넷 중 셋(Astra·Luna·Sol)이 3번 연못 프리셋에서 앞의 벚나무가 연못을 가립니다. 나무 위치가 시드로 정해지는데 프리셋 좌표는 고정이라, 시드에 따라 이렇게 될 수 있습니다. 브라우저로 확인했더라도 기본 시드 하나만 봤다면 놓칩니다.

### 4. 첫 화면 프레이밍

섬 반지름 22에 탑 높이 30이 넘으면 화각 45°에서 카메라를 꽤 멀리 빼야 전체가 들어옵니다. Luna와 Terra는 섬이 잘렸고, 정답지도 처음엔 잘렸습니다.

### 5. 프레임 누적 이징

`flight.t += dt`로 카메라 이동을 진행하면, 창이 백그라운드로 가서 프레임이 떨어질 때 1.2초짜리 연출이 십수 초로 늘어납니다. 60fps에서는 문제가 안 보이지만 저사양·백그라운드에서 갈립니다.

| 방식 | 결과물 |
|---|---|
| 벽시계 (`performance.now()`) | Opus, Sonnet, Gemini, CLI Astra, CLI Luna, Codex 앱 넷 전부, 정답지(수정 후) |
| 프레임 누적 (`dt`) | CLI Sol, CLI Terra, DeepSeek, qwen |

브라우저로 자기 결과물을 봤는지와는 관계가 없습니다. CLI Astra·Luna는 보지 못했는데도 벽시계로 짰고, CLI Sol·Terra는 같은 조건에서 `dt` 누적으로 짰습니다.

## 측정상 주의

검증에 쓴 브라우저 패널이 백그라운드로 가면 `requestAnimationFrame`이 초당 1–6틱으로 쓰로틀됩니다. 이 상태에서 프리셋을 누르면 카메라가 안 움직이는 것처럼 보여 **결함으로 오판하기 쉽습니다.** 실제로 검증 중 세 번 그럴 뻔했습니다. 그래서 프리셋 판정은 rAF 레이트를 먼저 재고, 쓰로틀 상태면 30초 이상 기다려 최종 위치를 확인했습니다. qwen의 프리셋 결함만 60fps 상태에서 재현해 판정했습니다.

Codex 앱 Sol은 처음 열었을 때 "GROWING YOUR GARDEN" 로딩 화면에서 멈춘 것처럼 보였습니다. 로딩 화면을 첫 `requestAnimationFrame` 콜백에서 걷는 구조라, 쓰로틀로 rAF가 멈추면 그대로 남습니다. 브라우저 패널을 앞으로 띄우자 정상으로 로드됐습니다. Codex 앱 네 개의 프리셋은 전부 패널을 띄운 상태(144fps)에서 판정했습니다.
